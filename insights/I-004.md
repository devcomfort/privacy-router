# I-004: Per-Model vLLM Sweep Analysis

## Summary
모델별 최적 max_num_seqs 탐색 완료. **메모리가 아닌 compute가 병목.**

## Key Insights

### 1. Throughput 곡선의 공통 패턴
```
seqs 증가 → throughput 증가 → 최적점 → throughput 감소
```
원인: KV cache contention이 아닌 **scheduler compute contention**.

### 2. 모델별 최적점
| Model | Weights | KV/token | Optimal seqs | Throughput | Accuracy |
|---|---|---|---|---|---|
| E2B | 9.6 GiB | 35 KiB | **32** | **4.38/s** | 65.0% |
| E4B | 14.9 GiB | 84 KiB | **24** | **2.92/s** | 60.0% |
| EXAONE | 2.4 GiB | 60 KiB | 32 | 4.94/s | 0.0% |

### 3. 메모리는 병목이 아님
vLLM 로그: E2B → 1788 동시 시퀀스 수용 가능
실제 최적: 32 (이론의 1.8%)
→ **max_num_seqs는 메모리 제한이 아닌 throughput 튜닝 노브**

### 4. gpu_utilization=0.87의 의미
- 이번 실행에서 vLLM이 측정한 free(106.84)/total(121.62) 기준 안전 상한 (환경 의존적)
- 다른 프로세스 종료 시 더 높은 값 가능; 0.87은 하드웨어 한계가 아님
- **실질적 영향: 없음** (메모리가 병목이 아니므로)

### 5. 가중치 무게 ≠ 최적 seqs
E2B(9.6GiB) > E4B(14.9GiB) 순서로 최적 seqs가 높지만,
이는 메모리가 아닌 **모델 forward pass 속도** 때문:
- E2B forward: ~30ms → 높은 concurrency 가능
- E4B forward: ~50ms → 낮은 concurrency에서 최적

| E2B | 32 | 4.38/s | 65.0% |
| E4B | 24 | 2.92/s | 60.0% |

### Profile B: Shared (40GB+ occupied)
| Model | seqs | Rationale |
|---|---|---|
| E2B | 16 | Solo의 50% |
| E4B | 12 | Solo의 50% |
| 12B | 8 | Solo의 50% |

## Methodology Lesson
- **Naive KV 공식**은 sliding-window 모델에서 2.6x 과소 추정
- **vLLM 시작 로그**의 "GPU KV cache size"가 ground truth
- **실제 sweep**이 최적 seqs를 결정하는 유일한 신뢰할 수 있는 방법
